# 위키 문서 작성 규칙

KMYARD 위키(Confluence) 문서를 작성, 수정할 때 따르는 규칙. 2026-10-06 사용자와 40개 규칙을 하나씩 합의해 확정함.
용어는 `docs/wiki-glossary.md`를 따름.

## 문서 유형

| 유형 | 담는 내용 |
| --- | --- |
| 상위 기획 | 목적과 왜 하는가, 개요, 용어, 문제점, 결정 필요 사항 |
| 세부 정책 | 상위 기획의 문제를 어떻게 풀 것인가. 해결 방식, 권한, 체계, 운영 방침 |
| 세부 기획 | 상위 기획과 세부 정책이 정리된 뒤의 화면 단위 기능 설명. 어느 페이지에서 무엇을 누르면 어떻게 되는지, 페이지 구성, 팝업과 저장 위치 등 |

## A. 문체

1. 서술은 개조식(~함/~됨/~임)으로 쓰고 합니다체는 쓰지 않음. 표 셀은 명사형도 허용함.
2. 대시("ㅡ", "—")와 하이픈("-")을 쓰지 않음. 범위는 "~", 복합어는 붙이거나 띄어 씀. 예외 2가지: 화살표 "->"는 하나의 기호로 허용, 표의 빈 값 표시는 셀 전체가 "-" 하나일 때만 허용(규칙 26).
3. 문단 사이에는 빈 줄을 넣지 않고 줄바꿈 한 번만 씀. 위키에서는 `<p>` 사이 간격 대신 `<br/>`로 이음.
41. 표 밖의 서술 문장은 문장 하나당 1단계 불릿(위키의 실제 불릿 목록, `<ul><li>`) 하나로 씀. 하이픈 글자("- ")를 직접 쓰지 않음. 예) 문장 2개짜리 문단 -> 불릿 2개. 제목, 표, 메타 블록, 이미지, 매크로, 코드는 대상 아님. 표 셀 안은 기존처럼 `<br/>`로 이음. 불릿은 중첩하지 않음(규칙 18). 규칙 3의 "줄바꿈 한 번"은 표 셀 안과 불릿 안(한 문장이 길어 줄이 나뉘는 경우)에만 해당함.
4. 주제 구분은 굵은 라벨이 아니라 하위 제목(h3)을 씀. 제목 단계는 h1(대분류) -> h2(소분류) -> h3(주제)이며 단계를 건너뛰지 않음(h1 바로 아래에 h3 금지). 표 셀 안에서는 제목을 쓸 수 없으므로 "수정 사항: ..."처럼 굵게 하지 않은 평문 줄로 씀. 굵은 글씨는 문장 안의 핵심 용어 강조에만 씀.
5. 채널, 역할명은 약칭 없이 풀네임으로 씀. 예) '센터/톡' 금지 -> '알림센터/알림톡'. 화면 라벨을 그대로 인용할 때만 화면 표기 허용.

## B. 구조

6. 상위 기획, 세부 정책 문서는 맨 앞에 "~란? / 왜 필요한가"를 두고 물류 초보자도 이해할 수준으로 풀어 씀. 세부 기획(기능 명세) 문서는 도입부 없이 바로 기능 설명으로 들어감.
7. "이유" 섹션에는 동기만 쓰고, "~해야 함" 식의 기능 요구사항은 상세 섹션에 따로 씀.
8. 섹션 순서는 화면 노출 순서보다 이해하기 쉬운 논리/중요도 순서를 우선함. 화면 순서는 참고만 함.
9. 상위 기획은 개념, 동선, 규칙만 쓰고 화면/템플릿 스펙은 세부 기획으로 보냄. 같은 내용을 두 문서에 중복해서 쓰지 않고 "N.N 제목 참고"로 연결함.
10. 문서 번호와 제목은 임의로 바꾸지 않음. 바꾸면 번호↔페이지ID 표와 다른 문서의 참조 링크도 같이 갱신함.
21. 문서 맨 위에 메타 블록(문서 유형, 상위/하위 문서, 최종 수정일, 확정 상태)을 표 한 줄로 둠.
22. 문서 하단에 "결정 필요 사항" 섹션을 두고, (제안)/미결 항목을 모아 정리함. 확정되면 본문에 반영한 뒤 표에서 제거함.
23. 문서는 상위 기획 / 세부 정책 / 세부 기획 3유형으로 나누고 위 "문서 유형" 표의 내용을 담음.
24. 한 문서에 주제가 2개 이상 섞이면 문서/섹션 분리를 제안함. 분리는 직접 하지 않고 제안만 하며, 표 행 수 기준은 두지 않음.

## C. 내용의 정직성

11. 본문은 구현 현황이 아니라 "의도한 스펙"(정답지)으로 씀. 표 비고에 미구현 표시는 허용하고, "현재는 ~임" 식 서술은 현황 섹션에만 둠.
12. 사용자가 확정하지 않은 정책은 "(제안)" 또는 "미결"로 표시하고 확정된 것처럼 쓰지 않음. 제안 항목은 다른 문서로 옮기지 않음.
13. 확인되지 않은 사실(화면, 코드, 데이터)은 비워 두지 않고 추정값을 적은 뒤 "(미확인)"을 붙임. 반영 후 보고할 때 "(미확인)" 항목 목록을 함께 알림.
14. 용어는 확정된 것만 씀. 새 용어는 먼저 제안하고, 확정되면 전체 문서에 반영함.
27. 확정 용어는 `docs/wiki-glossary.md`에 모음. 새 용어는 제안 -> 확정 후 용어집에 등록함.
36. 수치와 정책(시간, 횟수, 기한)은 코드나 설정값과 대조해서 쓰고, 대조하지 못하면 "(미확인)"을 붙임. 값이 다르면 임의로 고치지 않고 불일치를 보고한 뒤, 사용자 결정에 따라 규칙 20으로 코드를 같이 수정함.

## D. 표현 방식

15. 규칙은 표로, 예시는 "예)" 한 줄로, 흐름은 "A -> B -> C"로 씀.
16. 판단 기준(어떤 화면 입력란/권한 -> 어떤 대상)은 표에서만 자세히 명시함. 본문 서술은 간단히 씀.
17. 모든 규칙에는 "대상이 없을 때"(예외, 기본 동작)를 같이 씀.
18. 중첩 불릿은 쓰지 않고 h3, 표로 대체함. 불릿은 1단계만 씀.
25. 표 컬럼 순서는 표 유형별로 내용에 맞게 정함. 화면 항목표는 "항목 | 타입 | 데이터 | 동작 | 비고"를 기본으로 참고함. 의미가 겹치는 컬럼은 합치고, 행 하나에는 항목 하나만 씀.
26. 빈 값 표기: 데이터 값이 없으면 "null", 적용 대상이 아니면 "해당 없음" 또는 "미발송"처럼 해당하지 않음을 뜻하는 단어, 표의 빈 값에 한해 셀 전체가 "-" 하나인 표기도 허용함. 표에서 "-"를 쓰면 범례에 "하이픈(-) = 보내지 않음"처럼 풀어서 적음.
28. 숫자와 단위 사이를 띄어 씀. 예) 180 초, 1,000 원, 30 일, 3 회, 뒤 4 자리. 숫자는 아라비아 숫자, 금액은 천 단위 쉼표. 시각은 "매일 10시"처럼 붙여 씀.
29. 상태값, 버튼명, 필드명은 화면 표기 그대로 따옴표로 감쌈. 예) '접수 확인', '배차요청(F3)'. 일반 개념어는 따옴표 없이 씀.
30. 모든 규칙 섹션에 정상 케이스 예시 1개와 예외 케이스 예시 1개를 "예)" 한 줄로 둠.
31. 복잡한 흐름(동선, 상태 전환, 다단계 위탁)은 표나 다이어그램을 먼저 두고 설명은 그 뒤에 씀. 다이어그램은 draw.io로 직접 만들어 반영하고, 사용자가 그린 것이 있으면 그대로 유지함. 반영 후 사용자가 렌더링을 확인하도록 안내함.
32. 다단계 위탁처럼 헷갈리는 케이스는 고정 예시 체인을 재사용함: 화주 A -> 운송사 B -> 협력사 C -> 협력사 D(소속 기사 배차).
33. 문서 간 참조는 "N.N 제목" 형식으로 쓰고 위키 내부 링크(`ac:link`)를 같이 검. 번호만 쓰지 않음.

## E. 작업 절차

19. 채팅으로 초안을 제안하기 전과 이후 수정하기 전에 매번 위키 최신본을 다시 읽음(사용자가 직접 고친 내용 보존). 수정 요청이 오면 바로 위키에 반영하고, 반영할 때마다 페이지 댓글에 "이전 내용 / 수정한 내용"을 남김.
20. 위키를 고치면 같은 스펙이 걸린 로컬 코드와 연관 문서도 같이 수정함. 코드를 바꿀 때는 어떤 파일을 바꿀지 먼저 알림. 반영 후 "무엇을 바꿨고 무엇이 미확인인지"를 요약 보고함.
34. 저장할 때마다 페이지를 다시 읽어 표 깨짐, 줄바꿈, 이미지 구조를 확인함. 화면 렌더링 자체는 확인할 수 없으므로 사용자가 확인함.
35. 저장 전에 자체 점검(하이픈, 약칭, 빈 줄, 중첩 불릿, "(미확인)" 표시)을 돌려 위반 0건으로 만든 뒤 반영함. 점검 결과는 보고에 한 줄로만 적음.
37. 큰 구조 변경(섹션 이동, 삭제)은 반영 전에 "무엇이 어디로 가는지" 한 줄 요약을 먼저 보여주고 진행함. 규칙 19의 "수정 요청은 바로 반영"의 예외임.
38. 삭제하거나 이동한 내용은 댓글의 "이전 내용"에 그대로 보존함.
39. 위키 수정 후 바뀐 용어나 규칙이 걸린 연관 문서의 영향 목록을 보고하고, 영향받는 문서도 바로 같이 수정함. 수정한 문서마다 댓글에 이전/수정 내용을 남김.
40. 여러 문서를 고쳐야 하면 "어느 문서를 무엇 때문에 어떻게 고칠지" 목록을 먼저 알린 뒤 진행함. 요청한 문서를 먼저 수정함.
